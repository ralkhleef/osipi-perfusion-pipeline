    Requirements

    Docker and Git are the only things required to run the application. Python and Node are needed only to run the test suites, which run outside the container.

    To run the application

    Nothing else is required.

    Docker Desktop
    Must be running before docker build. Also supplies the daemon the Run step uses.
    Git
    Or download the ZIP from GitHub, which works equally well.

    To run the tests

    The suites run outside the container.

    Python 3.10 or newer
    Not needed to run the application. The image ships its own Python 3.11.
    Node 18 or newer
    Built-in modules only, so there is no npm install.

    Getting the code

    Clone
    git clone https://github.com/ralkhleef/osipi-perfusion-pipeline.git
cd osipi-perfusion-pipeline

    Every command below is run from that directory. The clone contains no imaging data: reference maps, ROI masks and submissions are excluded from version control, so a fresh clone starts empty and you supply the data yourself.

    DirectoryHolds
    backend/The FastAPI application and its services
    frontend/The browser interface, in plain HTML, CSS and JavaScript with no build step
    src/osipi_pipeline/The library: ingestion, validation and scoring
    config/Challenge rules, the file you edit to change requirements
    data/ created on first runReference data, masks, scoring packages and outputs
    submissions/ created on first runUploaded archives and their extracted contents
    tests/Python and frontend test suites

    Start it

    One command. It builds the image the first time, which takes a few minutes, then starts the application. There is no separate install step: the image brings its own Python and dependencies.

    Start
    docker compose up --build

    Leave it running. When you see Uvicorn running on http://0.0.0.0:8000 the application is up. To stop it, press Ctrl-C in that terminal.

    That is the whole installation. The commands further down this page are optional: one alternative way to start it, and the test suites, which only a developer changing the code needs to run.

    Open it

    Go to http://localhost:8000 in a browser. The interface opens on step 1 of 6, Upload.

    To check it end to end, upload a submission and walk the six steps. Nothing is sent anywhere: the application runs on your machine and the files stay there.

    1

    Enter a team name and pick the challenge

    Anything will do for a first run. The challenge decides which rules apply.

    2

    Drop in a ZIP of parameter maps

    Then work down the steps on the left. Each one unlocks when the last finishes.

    3

    Export the report

    If a report comes out at the end, the installation is working.

    Reference maps and ROI masks are organiser data and are not in the repository. Without them you get validation and quality control; the comparison against ground truth needs them. See Reference data and masks.

    If it does not start

    Cannot connect to the Docker daemon

    Docker Desktop is not running. Start it, wait for the whale icon to settle, then run the command again.

    Port 8000 already allocated

    Something else is using the port. Edit the ports line in docker-compose.yml to "8080:8000" and open http://localhost:8080 instead.

    It starts, but the Run step says Docker is unavailable

    Only affects running a participant's code. Upload, validation, quality control, previews and export all still work. It means the Docker socket mount or the HOST_* variables in docker-compose.yml did not reach the container.

    I edited the challenge rules and nothing changed

    Press Reload rules in Scoring Setup. See Apply a change.

    Starting it another way

    You do not need this if docker compose up --build worked. It is here for anyone without Docker Compose. It does exactly the same thing.

    Build
    docker build -t osipi-pipeline .
    Run
    docker run --rm -p 8000:8000 \
  -v "$PWD/data:/app/data" \
  -v "$PWD/submissions:/app/submissions" \
  -v "$PWD/config:/app/config:ro" \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -e PYTHONPATH=/app/backend:/app/src \
  -e HOST_SUBMISSIONS_DIR="$PWD/submissions" \
  -e HOST_OUTPUTS_DIR="$PWD/data/outputs" \
  -e HOST_REFERENCE_DATA_DIR="$PWD/data/reference_data" \
  osipi-pipeline

    On Windows PowerShell, replace $PWD with ${PWD} and the trailing backslashes with backticks.

    The three HOST_* variables and the Docker socket mount are what let the container start a second container for a participant's code. The backend runs inside Docker but calls the host daemon, so the paths it passes to docker run have to be host paths, not container paths. The config mount is what makes Reload rules able to see an edit.

    Running the tests

    Only needed if you are changing the code. You do not have to run any of this to use the application.

    The suites run outside the container, against the source in the working tree, so they need their own dependencies on your machine. This is the only place anything is installed with pip.

    Python tests
    pip install -r requirements.txt -r backend/requirements.txt -r requirements-test.txt
python3 -m pytest -q

    The frontend suites are plain Node scripts using only built-in modules, so there is no package to install. Each prints its own pass and fail counts and exits non-zero on a failure.

    Frontend tests
    node tests/frontend_smoke_test.js
node tests/frontend_roi_dom_test.js
node tests/frontend_header_check_test.js
node tests/frontend_config_maps_test.js
node tests/frontend_run_outcome_test.js
node tests/frontend_auto_advance_test.js
node tests/frontend_config_changes_test.js
node tests/frontend_config_preview_test.js
node tests/frontend_config_assets_test.js
node tests/frontend_validation_card_test.js
node tests/footer_logic_test.js

    To exercise the whole pipeline rather than its parts, run the demo. It builds a DCE submission, puts it through upload, validation, analysis and export, and writes the reports and CSVs to data/outputs/demo_evidence/ along with a summary of what it checked. It extracts into a temporary directory, so it leaves no submissions behind.

    End-to-end demo
    python3 scripts/demo_evidence.py

    Updating your copy

    The application is served from inside the Docker image, and the browser interface is copied into that image when it is built. Neither is read live from disk. So pulling new code changes nothing you can see until you rebuild, and rebuilding changes nothing you can see until the browser drops its cached copy. Both steps are needed, in that order.

    Update and restart
    cd osipi-perfusion-pipeline
git pull
docker compose up -d --build

    Then reload the page in the browser. A plain refresh often keeps the old JavaScript, so use a cache-clearing reload: open DevTools, right click the reload button, and choose Empty Cache and Hard Reload. In Firefox and Safari, hold Shift and click reload.

    If the interface looks unchanged after all that, it is almost always one of these three, in order of likelihood: the browser served a cached script, the image was not rebuilt, or the container was never restarted. The check below distinguishes them without guessing.

    Check what the server is actually serving
    python3 scripts/diagnose_run_analysis.py

    It reports whether the running application is serving the current interface or an older copy, and prints the fix for whichever case it finds.

    What each kind of change needs

    What you changedWhat you need to do
    frontend/, backend/, src/ Rebuild the image, then a cache-clearing reload
    config/validation_rules.yaml Nothing. The folder is mounted, so edits are picked up. Use the reload button in the Configuration Manager, or restart the container.
    Files under data/ or submissions/ Nothing. Both are mounted from disk, not copied into the image.
    requirements.txt, Dockerfile Rebuild. The dependency layer is cached, so this one takes longer.

    If you have your own edits

    git pull refuses to overwrite uncommitted work, which is a feature rather than an obstacle. To see what is yours before pulling:

    See your changes
    git status
git diff

    Commit them, or set them aside and bring them back after the pull:

    Set aside, update, restore
    git stash
git pull
git stash pop

    Your imaging data is never at risk from any of this. Reference maps, ROI masks and submissions are excluded from version control, so git pull and git stash do not touch them.

    Confirming the update worked

    Full check
    python3 scripts/preflight.py

    This walks a generated submission through all six steps against the running application and prints one line per step. It uploads nothing real and removes what it creates. If every check passes and the browser still looks wrong, the problem is the browser rather than the pipeline.
