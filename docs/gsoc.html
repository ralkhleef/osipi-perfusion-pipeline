    The project

    Python Pipeline for Evaluating OSIPI Perfusion Imaging Challenge Submissions.

    By Ranya Al-khleef, mentored by Lena Václavů, Olivia Jones and Puneet Kumar, for OSIPI and the ISMRM Perfusion Study Group. A 175 hour project. The code is on GitHub.

    Two implementations given the same DCE scan return different Ktrans values. OSIPI runs challenges to quantify those differences, which requires every submission to be checked and scored identically and reviewed without knowledge of its origin. This project provides that pipeline. See How it works for the design.

    What shipped

    • Import from a ZIP archive, a folder, a GitHub repository or a Zenodo record, with batch archives separated automatically.
    • Single-pass indexing that assigns every file a role and a scan identity, resolved from the directory structure.
    • File-level and structural validation covering eleven distinct issue codes.
    • Execution of submitted code in Docker with no network access, a memory limit and a timeout.
    • Reference comparison producing RMSE, mean absolute error, bias and correlation, voxelwise and per ROI.
    • Within-scan ROI median, population standard deviation and coefficient of variation.
    • HTML and PDF reports generated from one result model, so the two cannot diverge.
    • Blinded exports with no identifying information in the document, its metadata or its filename.

    Still open

    Each item below is blocked on a definition or an input that only the challenge leads can supply, rather than on remaining development time. Values that cannot be computed are reported as unavailable.

    • Accuracy and deviance. The definition. Accuracy may refer to signed bias, RMSE, or absolute or percentage error.
    • Standard deviation and CoV across repeats, sites and participants. Whether to aggregate scan-level ROI medians or pooled voxel values, and whether repeats and sites are paired within a participant first. The implementation exists and is disabled pending those decisions.
    • Residual sum of squares. The measured dynamic signal. Submissions supply the modelled signal only.
    • ICC. The ICC model, and whether repeated datasets are provided.
    • ASL and DSC completeness rules. The required maps and dataset grid for each. The map types are configured; the challenge entries are empty.
    • BIDS validation. Not implemented. NIfTI checks cover readability, dimensionality and value sanity.

    Who changes what

    Ongoing maintenance was designed to sit with the challenge team rather than with a developer. The boundary is arithmetic: what a challenge requires and which script scores it are configuration, while a new formula is code.

    The challenge team can change these

    No developer, no terminal.

    Install or replace a scoring script
    Upload the ZIP in Scoring Setup, then select it for the challenge.
    Change which metrics it reports
    Edit manifest.json inside that ZIP, in any text editor.
    Required maps, dataset counts, filename aliases
    Edit config/validation_rules.yaml, then press Reload rules.
    Enable the grouped SD and CoV
    One setting, once the two conventions are confirmed.

    These need a developer

    Python, with accompanying tests.

    A metric that does not exist yet
    Accuracy, deviance, residual sum of squares and ICC each need to be written and tested once their definitions are agreed.
    A form for editing the rules
    Configuration is still YAML in a text editor. A form would need the config directory mounted writable and a save path that cannot corrupt the file.

    Testing

    The suite comprises 704 Python tests and 1,125 frontend checks. Seven production defects were found by running a real archive through the interface rather than by the suite, including a DCE archive that split into two submissions, shared files deleted during the batch separation, ROI masks counted twice on case-insensitive filesystems, and a team name printed in a blinded report. Each fix carries a regression test, and each test was verified by reintroducing the defect to confirm the test detects it.

    A single command exercises the pipeline end to end and writes the reports, the result files and a record of the checks it performed:

    Demo
    python3 scripts/demo_evidence.py

    See Example output for a report it made.
