    Summary

    A Python pipeline for evaluating OSIPI perfusion imaging challenge submissions.

    Ranya Al-khleef, mentored by Lena Václavů and Olivia Jones, for OSIPI and the ISMRM Perfusion Study Group. 16 May to 18 August 2026.

    This local web application imports challenge submissions, checks their files, runs submitted code in Docker when needed, calculates QC and reference comparisons, and exports blinded results. It supports DCE, ASL, and DSC.

    Goals

    Different analysis methods can produce different parameter maps from the same perfusion scan. OSIPI challenges compare these results using the same review process for each submission.

    The project goals were:

    • Accept a submission, whether it contains finished maps or the code that produced them.
    • Check it against the rules for its challenge and report any validation issues.
    • Run submitted code in a controlled environment.
    • Compute quality control, and comparison against ground truth where it exists.
    • Produce blinded reports without team or contact details.
    • Let the challenge leads change the rules without editing Python.

    What I did

    The interface takes a submission through six steps: Upload, Review, Validate, Run, QC and Preview, Export.

    Ingestion
    Import from a ZIP, folder, GitHub repository or Zenodo record. Archives holding several teams are separated automatically.
    Identity
    Every file is given a role and a scan identity of dataset, participant, site and repeat, read from the directory structure. Conflicts are reported rather than guessed at.
    Validation
    NIfTI readability, dimensionality and values, plus structural completeness against the challenge rules, with eleven issue codes.
    Execution
    Submitted code runs in Docker with no network, a memory cap and a timeout.
    Analysis
    Quality control per map. Against ground truth: RMSE, mean absolute error, bias and correlation, both voxelwise and within each ROI mask. Per region: median, mean, standard deviation, range and coefficient of variation.
    Header checks
    Shape, voxel size, orientation and data type compared against the ground truth, so a flipped submission is caught rather than scored as if it were correct.
    Reporting
    HTML and PDF generated from the same result model, plus CSV and JSON.
    Blinding
    Team name, contact, submission id and archive name absent from the document, its metadata and its download filename.
    Configuration
    Challenge rules in YAML, validated on load, editable in the app or the file, applied by a button without restarting anything.

    See Examples for the interface and How it works for the workflow in detail.

    What is left

    These items still need confirmation from the challenge leads. Results that cannot be calculated are shown as unavailable.

    • Metric definitions. Accuracy and deviance need formulas; accuracy could mean signed bias, RMSE, or absolute or percentage error. Whether the signal-time residual sum of squares stays raw or is normalised is open.
    • Variability across repeats, sites and participants. ICC(2,1) and ICC(3,1) are reported using ROI medians across repeats. The final grouping convention still needs confirmation.
    • Dataset grids for ASL and DSC. Whether either has one cohort or several, and the counts. The required maps are configured; the grid is not.
    • Thresholds and ranking. Pass and fail rules, the final ROI and mask sets, ranking aggregation, the required sections of a methods document, and which scoring package is designated official.
    • Full BIDS validation. Layout and naming are checked when a challenge enables it: the dataset description, subject and session directories, filename entities and the order BIDS fixes for them. The rest of the specification is not covered, and a submission passing these checks should be called structurally consistent rather than BIDS valid.

    Everything except the metric formulas is configuration. See Configuration.

    What I learned

    • Perfusion imaging. I started with very little background in brain anatomy or perfusion MRI. Learning how CBF, ATT and Ktrans are measured, and why two groups analysing the same scan can arrive at different answers, is what made the rest of the work make sense.
    • Designing for people who do not write code. The people running these challenges are researchers, not developers. Keeping the challenge rules in configuration, and the controls in the interface rather than in a terminal, did more for how usable the tool is than anything else I built.
    • Testing against real data. Running real submissions through the application found problems the automated tests had not, and changed how I write tests.
