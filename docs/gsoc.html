    The project

    Python Pipeline for Evaluating OSIPI Perfusion Imaging Challenge Submissions.

    ContributorRanya Al-khleef
    MentorsLena Václavů, Olivia Jones, Puneet Kumar
    OrganisationOSIPI, ISMRM Perfusion Study Group
    Length175 hours
    Codegithub.com/ralkhleef/osipi-perfusion-pipeline

    OSIPI runs perfusion-MRI challenges where teams submit parameter maps computed from a shared dataset. Reviewing those by hand does not scale: someone has to open each archive, work out which challenge it belongs to, check the files are present and readable, run the team's code, compute statistics, and assemble results that can be shared without revealing who submitted what. This project automates that.

    What shipped

    AreaWhat it does
    IngestionArchive, folder, GitHub and Zenodo import. One indexing pass per archive. Batch archives split automatically.
    IdentityDataset, participant, site and repeat read from the directory structure, with filename patterns as a fallback. Conflicts are reported, not guessed at.
    ValidationNIfTI readability, dimensions and finite values, plus structural completeness with eleven issue codes.
    ExecutionReproducible submissions run in Docker with no network, a memory cap and a timeout. Result-only submissions skip the step.
    Reference scoringRMSE, MAE, bias, error CoV and correlation against reference maps, whole-map and within each ROI mask.
    ROI statisticsWithin-scan Ktrans median, population SD and CoV, computed once and read by every output.
    ReportsHTML and PDF built from one model, so the two cannot disagree.
    BlindingTeam name, contact, submission id and archive name absent from the body, the metadata and the download filename.

    Still open

    These are not unfinished work in the sense of running out of time. Each one is waiting on a decision or an input that only the challenge leads can give. The pipeline reports an unavailable value as unavailable, and does not compute a metric whose formula has not been agreed.

    ItemWhat is missing
    Accuracy, devianceThe definition. Accuracy could mean signed bias, RMSE, or absolute or percentage error.
    Inter-participant, inter-repeat and inter-site SD and CoVWhether to aggregate scan-level ROI medians or pooled voxel values, and whether repeats and sites are paired within a participant first. The code exists and is switched off.
    Residual sum of squaresThe measured dynamic signal. Submissions carry the modelled signal only, and RSS needs both.
    ICCWhich ICC model, and whether repeatability comes from repeated noise-varied datasets.
    ASL and DSC completeness rulesWhich maps each challenge requires and the dataset grid. The map types are configured; the challenge entries are empty.
    BIDS validationNot implemented. NIfTI checks are readability, dimensions and value sanity only.

    Who changes what

    Most of what a challenge team will want to change after this project ends needs no developer. The line is drawn at arithmetic: what a challenge requires and which script scores it are configuration, while a new formula is code.

    ChangeHowNeeds a developer
    Install or replace a scoring scriptUpload the ZIP in Scoring Setup, then select it for the challengeNo
    Change which metrics a script reportsEdit manifest.json in the ZIP, any text editorNo
    Change required or optional mapsEdit config/validation_rules.yaml, then press Reload rulesNo
    Change participant, repeat or site countsSame file, same buttonNo
    Add a filename aliasSame file, same buttonNo
    Turn on the grouped SD and CoV statisticsConfirm the two open conventions, then a config flagNo, once the conventions are agreed
    Define a new metric, such as accuracy or ICCPython, with testsYes

    Editing the rules used to mean restarting the container, which meant a terminal. There is now a Reload rules button in Scoring Setup that re-reads the file and reports a mistake on screen. A rejected edit changes nothing: the configuration already running stays running until a valid one replaces it.

    What is not covered: the rules are still edited as YAML in a text editor, not through a form. That is the obvious next improvement, and it needs the config directory mounted writable and a save path that cannot corrupt the file.

    Testing

    693 Python tests and 1,125 frontend checks. More useful than the count: seven production bugs were found by running a real archive through the real interface, not by the suite. Among them, a DCE archive split into two submissions, shared root files were destroyed during the batch carve, ROI masks were counted twice on macOS, and the blinded report printed the team name in its Affected column. Each fix has a regression test, and each test was checked by deliberately breaking the fix to confirm the test notices.

    A single command runs the whole pipeline end to end and writes the reports, the CSVs and a summary of what it verified:

    Demo
    python3 scripts/demo_evidence.py

    See Example output for a report it produced.
