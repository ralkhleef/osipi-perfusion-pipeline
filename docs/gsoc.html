    The project

    Python Pipeline for Evaluating OSIPI Perfusion Imaging Challenge Submissions.

    ContributorRanya Al-khleef
    MentorsLena Václavů, Olivia Jones, Puneet Kumar
    OrganisationOSIPI, ISMRM Perfusion Study Group
    Length175 hours
    Codegithub.com/ralkhleef/osipi-perfusion-pipeline

    Two labs given the same DCE scan will produce two different Ktrans maps. OSIPI runs challenges to measure how far apart those answers are, which only works if every submission is checked and scored the same way. This project is the software that does that, and that keeps the team's name out of the reviewer's copy. See How it works.

    What shipped

    • Import from a ZIP, a folder, GitHub or Zenodo. Batch archives split on their own.
    • Every file gets a job and a scan address, read from the folders first.
    • Checks on the files and on the submission as a whole, with eleven issue codes.
    • Submitted code runs in Docker with no network, a memory cap and a time limit.
    • RMSE, mean absolute error, bias and correlation against the reference, per voxel and per ROI.
    • Per-ROI median, SD and CoV for each scan.
    • HTML and PDF built from one set of results, so the two cannot disagree.
    • Blinded exports with no team name in the page, the metadata or the filename.

    Still open

    None of these ran out of time. Each is waiting on something only the challenge leads can give. Nothing here is guessed at: a value that cannot be worked out is written as unavailable.

    ItemWhat is missing
    Accuracy, devianceThe formula. Accuracy could mean bias, RMSE, or absolute or percentage error.
    SD and CoV across repeats, sites and participantsTwo conventions. The code is written and switched off.
    Residual sum of squaresThe measured signal. Submissions carry the modelled one only.
    ICCWhich model, and whether repeated datasets are supplied.
    ASL and DSC rulesWhich maps each needs. The map types are set up, the challenge entries are empty.
    BIDS validationNot built. NIfTI checks cover readability, shape and values.

    Who changes what

    Most of what a challenge team will want to change later needs no developer. The line is drawn at arithmetic: what a challenge asks for and which script scores it are settings, while a new formula is code.

    ChangeHowNeeds a developer
    Install or replace a scoring scriptUpload the ZIP in Scoring Setup, then pick it for the challengeNo
    Change which metrics it reportsEdit manifest.json in the ZIP, any text editorNo
    Change required maps, dataset counts or filename aliasesEdit config/validation_rules.yaml, then press Reload rulesNo
    Turn on the grouped SD and CoVAgree the two conventions, then a settingNo, once agreed
    Define a new metric such as accuracy or ICCPython, with testsYes

    The rules are still edited as YAML in a text editor rather than through a form. That is the obvious next thing to build.

    Testing

    704 Python tests and 1,125 frontend checks. The more useful number is seven: production bugs found by pushing a real archive through the real interface, which the suite had not caught. A DCE archive split into two submissions. Shared files were deleted during the batch split. ROI masks counted twice on macOS. The blinded report printed the team name. Every fix has a test, and every test was checked by breaking the fix on purpose to see whether the test noticed.

    One command runs the whole thing and writes the reports, the CSVs and a list of what it checked:

    Demo
    python3 scripts/demo_evidence.py

    See Example output for a report it made.
