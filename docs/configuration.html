    In-app Configuration Manager

    Reviewer/admin users can manage DCE, ASL and DSC requirements from QC & Preview → Reviewer / Admin: Scoring Setup → Challenge Configuration Manager. The editor covers required and optional maps, expected dimensions, filename aliases, required documents and outputs, participant/repeat/site counts, whether participant code execution is required, the reference-dataset version, and the selected provider-specific scoring package.

    The safe workflow is Test Configuration → Preview Changes → Save as New Version → Activate. Testing and previewing are side-effect free. Saving creates an inactive, immutable local version. Activation re-tests the saved version before atomically replacing active rules; a failure restores the previous YAML and scoring selection. Version history provides the same tested activation path for rollback.

    The manager also shows local private reference maps, masks and measured signals, plus a challenge capability matrix. Configuration ZIP export includes rules, version metadata, scoring selection and a public manifest when applicable. It excludes private images, masks, measured signals, scoring code and other organiser data. Import saves a new inactive version and never silently activates it.

    PDF, HTML and JSON results record analysis provenance: challenge, active challenge configuration version, scoring package, pipeline version, reference-dataset version and analysis date. Give each released reference dataset a stable version label so a later reviewer can reproduce which assets were intended without exposing their private paths.

    No terminal or YAML editor is required for routine handoff updates. Direct YAML editing remains supported for developers, and the existing Reload rules button remains available for that route.

    1. Changing challenge requirements

    Challenge structure is in config/validation_rules.yaml. Required and optional maps, artifacts, dimensions, dataset structure, aliases, and filenames belong there. A new scientific formula belongs in implemented and tested analysis/scoring code or a versioned trusted package, not in YAML. The configuration is read from disk rather than compiled in, and validated on load: an unknown key, a malformed dataset block or a bad regular expression fails immediately rather than being ignored. Editing the file is not the whole job. Apply a change covers how the edit reaches the running application.

    Dataset structure

    Each dataset declares its expected participants, repeats and sites. Validation counts resolved scan identities against that grid. A null count is not checked, which is how an undecided number is expressed.

    Example: change expected participant, repeat or site counts

    config/validation_rules.yaml
    challenges:
  dce:
    datasets:
      synthetic:
        participants: 4      # was null, now checked
        repeats: 2
        sites: 3
      clinical:
        participants: 5
        repeats: 2
        sites: 1

    That grid expects 24 synthetic scans (4 × 2 × 3) and 10 clinical (5 × 2 × 1). A shortfall is reported as DATASET_COUNT_MISMATCH.

    Map requirements

    A missing required map is a blocking error. An optional map is never reported as missing. Non-map artifacts such as a 4-D modelled signal-time curve or a methods document are declared under artifact_types and required per challenge. Where an artifact declares dimensions, the value is checked against the NIfTI header.

    The current ASL rules require CBF and ATT. The current DSC rules require CBV, CBF and MTT. Their missing maps are blocking errors, not legacy expected-map warnings.

    DCE also recognises an optional 4-D measured_st artifact. When one measured and one modelled signal can be matched to the same scan, the pipeline computes raw voxelwise Residual Sum of Squares (RSS) across time and summarizes it for the whole image and compatible ROIs. RSS is descriptive and is not labelled deviance.

    The challenge's analysis block controls which built-in analyses are enabled and maps their inputs to configured map and artifact ids. Scientific formulas remain in tested Python; changing labels or aliases cannot silently change a calculation.

    config/validation_rules.yaml
    analysis:
  roi_descriptive:
    enabled: true
    map_types: [ktrans]
  signal_rss:
    enabled: true
    modelled_artifact: modelled_st
    measured_artifact: measured_st

    Enabled analyses must name their map or artifact inputs explicitly; there are no hidden challenge-specific fallback ids. Unknown analysis keys or input ids are rejected. Disabling one analysis does not disable readable-map QC, previews, or other compatible analyses.

    The DCE grouped_statistics block enables provisional grouping of scan-level ROI medians across participants, repeats and sites. It reports mean, population SD and CoV; exactly two clearly matched repeats or sites also receive a signed difference. These are not formal repeatability, ICC, pass/fail, or ranking results.

    Example: change ve from optional to required

    config/validation_rules.yaml
    challenges:
  dce:
    required_maps:
      - ktrans
      - ve             # moved up from optional_maps
    optional_maps:
      - vp
      - kep
    required_artifacts:
      - modelled_st    # 4-D, checked against the NIfTI header
      - methods

    Filename aliases

    Filename detection uses the patterns list on each map type. An alias affects detection and labelling only.

    Example: add another filename alias for Ktrans

    config/validation_rules.yaml
    map_types:
  ktrans:
    display: Ktrans
    label: Volume transfer constant
    units: min^-1
    dimensions: 3
    patterns:
      - ktrans
      - k_trans
      - transfer_constant
      - ktrans_map        # new alias

    Add a validation test covering the new alias.

    Challenge type names come from the same file. KNOWN_CHALLENGE_TYPES exists at runtime but is derived from the configuration at startup, not maintained by hand.

    2. Adding or updating scoring

    Three mechanisms are distinct. Generic reference comparison is part of the pipeline: it compares readable maps with compatible references and can run even when provider scoring mode is none. The built-in legacy TF6.2 provider is a bundled hook for its specific DCE Ktrans assets; it is not an uploaded package. It is offered only for DCE; ASL and DSC do not currently have compatible built-in providers. Trusted custom scoring packages are uploaded ZIPs selected per challenge.

    Provider mode none disables provider/official scoring, not generic QC, previews, exports, compatible DCE Ktrans ROI descriptive statistics, or compatible generic reference comparisons. Official provider output requires an approved provider and its organiser-owned assets. Official OSIPI challenge ranking is not currently configured.

    What a custom package contains

    A package is a ZIP holding the manifest and the script, plus any reference data the script needs. manifest.json may sit at the root or one level down, so an archive made by zipping a folder works without repacking.

    Package layout
    my_scoring_package.zip
  manifest.json      required
  scoring.py         the entry point; the name comes from manifest.entry_point
  requirements.txt   optional dependency declaration; not installed automatically
  reference/         optional, ground-truth NIfTI maps
  masks/             optional, ROI mask NIfTI files
  README.md          optional

    Installed packages live in data/scoring/packages/, one directory per package_id. Which package is active per challenge is recorded in data/scoring/active.json. Both are under data/, which is a mounted volume, so installing a package does not involve rebuilding the image.

    Example: scoring package manifest

    manifest.json
    {
  "package_id": "local_dce_ktrans_v1_0",
  "name": "Local DCE Ktrans analysis",
  "version": "1.0.0",
  "challenge_type": "dce",
  "map_type": "ktrans",
  "required_inputs": ["ktrans"],
  "required_assets": ["reference/Ktrans.nii.gz"],
  "entry_point": "scoring.py",
  "requirements_file": "requirements.txt",
  "call_mode": "standard",
  "official": false,
  "metrics": ["rmse", "bias"]
}

    call_mode is standard for scripts taking --submission-dir, --output-dir and optionally --reference-dir. Every metric declared in the manifest must be present in metrics.json or results.json. A requirements file is checked for presence but is not installed automatically. Anything that is not approved OSIPI scoring takes "official": false.

    call_modeHow the script is invokedUse when
    standardpython scoring.py --submission-dir <dir> --output-dir <dir> [--reference-dir <dir>]Writing a new script. The directories are passed in, so nothing is hardcoded.
    osipi_cwdRun with the working directory set to the package directory; the script resolves its own relative pathsAdopting an existing OSIPI script that expects the legacy TF6.2 layout, without editing it.

    challenge_type is checked at install against the challenges configured in config/validation_rules.yaml, and a manifest naming one that does not exist is rejected. So a new challenge is added to the YAML before its scoring package is uploaded. package_id is restricted to letters, digits, underscores and hyphens, because it becomes a directory name.

    Installation validates the JSON manifest, readable package version, known challenge, configured input ids, metric names, safe paths, entry point, declared assets, optional requirements file, and scorer syntax/importability. The ZIP is checked in a staging directory and is installed only after every check passes. Activation then verifies that the package is ready and belongs to the selected challenge. A failed validation or activation leaves the previous active configuration unchanged.

    An already-active legacy package can continue running, but its manifest must declare required_inputs before it can be uploaded or activated again under the stricter contract.

    Use a distinct versioned package_id for each release, such as dce_accuracy_v1_0 and dce_accuracy_v1_1. The selected package id, name, and version are stored in the active configuration, and completed package results also record the package version. Future analyses that are not installed remain unavailable; they do not stop the rest of the pipeline.

    A scoring package is Python that executes on the server. Read the script before installing one.

    3. Adding private reference data

    Reference maps and ROI masks come from the organiser. Search order: the submission's own reference/ directory, the configured reference data directory, then the active scoring package's reference directory.

    Within a reference root, maps are read from maps/ and masks from masks/. Files are de-duplicated by physical file identity rather than path text, so on macOS and Windows the same mask cannot be admitted twice under two spellings.

    Keep organiser source copies outside the repository or in the gitignored private_scoring_assets/ workspace. Generic comparison data may be copied to the gitignored data/reference_data/ paths. Package-specific assets should be copied into the relative paths declared by required_assets before the trusted ZIP is uploaded. Installed packages live under gitignored data/scoring/packages/. Never commit private masks, references, answer keys, or unreleased challenge data.

    QC and previews remain available for readable maps. DCE Ktrans ROI descriptive statistics can appear with compatible ROI masks, generic reference comparisons with compatible reference maps, and provider-specific analysis or scoring when configured with its required assets. Generic reference comparisons are not automatically official scores. Official OSIPI challenge ranking is not currently configured.

    4. Safe updates

    For routine organiser updates, prefer the in-app Configuration Manager above. It provides validation, a readable diff, version history, rollback, import/export and explicit activation. The file-based route below is retained for developers and advanced maintenance.

    Editing a file on your machine is not enough on its own. The application validates rule reloads and scoring packages before replacing the active configuration. What is needed depends on what you changed.

    What you changedTo apply itWhy
    config/validation_rules.yaml or config/settings.yamlPress Reload rules in Scoring SetupThe compose file mounts ./config, so the file is already current. The button re-reads it and drops everything cached from the old copy.
    The same, but running without the config mountdocker compose up --buildThe image holds its own copy taken at build time. Without the mount, that copy is the one in use and the button re-reads the same stale file.
    A scoring packageUpload a new versioned package, review validation, then activate it in Scoring SetupValidation and activation are separate. A failure leaves the previous active package unchanged.
    Reference maps or ROI masksAdd them through Reference Data & Masks in the Configuration Manager, or copy them into the documented local data/reference_data/ layoutThey remain local, are checked for NIfTI readability, and are excluded from configuration exports.
    Anything under backend/, frontend/ or src/docker compose up --buildSource is copied into the image, not mounted.

    A rules edit that appears to do nothing is almost always this: the file changed on disk but nobody pressed Reload, or the container is running the copy baked into the image because ./config is not mounted.

    Reload reports a bad edit on screen and changes nothing. Whatever configuration was running keeps running until a valid one replaces it, so a typo cannot take the pipeline down mid-review.

    Check the edit from a terminal

    The button is the normal route. If you would rather see the parsed result directly, or you are working outside the container, reading the file says whether it parses and what the application will see:

    Check
    PYTHONPATH=src python3 -c "
from osipi_pipeline.config.rules import datasets_by_challenge, map_type_specs
print(sorted(map_type_specs()))
print(datasets_by_challenge()['dce'])
"

    An invalid file raises ConfigValidationError naming the key at fault. A change to required maps or dataset counts also belongs in the test suite, so that a later edit reverting it fails visibly rather than quietly.
