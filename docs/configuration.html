    Validation rules

    Challenge requirements are in config/validation_rules.yaml, read at runtime. The file is validated on load: an unknown key, a malformed dataset block or a bad regular expression fails immediately rather than being ignored.

    The schema covers structure: which files are required, their dimensions, how scans are organised. A new statistical formula is implemented and tested in code.

    Annotated template: docs/examples/challenge.example.yaml.

    Dataset structure

    Each dataset declares its expected participants, repeats and sites. Validation counts resolved scan identities against that grid. A null count is not checked, which is how an undecided number is expressed.

    Example: change expected participant, repeat or site counts

    config/validation_rules.yaml
    challenges:
  dce:
    datasets:
      synthetic:
        participants: 4      # was null — now checked
        repeats: 2
        sites: 3
      clinical:
        participants: 5
        repeats: 2
        sites: 1

    That grid expects 24 synthetic scans (4 × 2 × 3) and 10 clinical (5 × 2 × 1). A shortfall is reported as DATASET_COUNT_MISMATCH.

    Map requirements

    A missing required map is a blocking error. An optional map is never reported as missing. Non-map artifacts — a 4-D modelled signal-time curve, a methods document — are declared under artifact_types and required per challenge. Where an artifact declares dimensions, the value is checked against the NIfTI header.

    Example: change ve from optional to required

    config/validation_rules.yaml
    challenges:
  dce:
    required_maps:
      - ktrans
      - ve             # moved up from optional_maps
    optional_maps:
      - vp
      - kep
    required_artifacts:
      - modelled_st    # 4-D, checked against the NIfTI header
      - methods

    Filename aliases

    Filename detection uses the patterns list on each map type. An alias affects detection and labelling only.

    Example: add another filename alias for Ktrans

    config/validation_rules.yaml
    map_types:
  ktrans:
    display: Ktrans
    label: Volume transfer constant
    units: min^-1
    dimensions: 3
    patterns:
      - ktrans
      - k_trans
      - transfer_constant
      - ktrans_map        # new alias

    Add a validation test covering the new alias.

    Challenge type names come from the same file. KNOWN_CHALLENGE_TYPES exists at runtime but is derived from the configuration at startup, not maintained by hand.

    Scoring providers

    A scoring provider is an uploaded package, not a registry entry in the source. Each package holds a scoring script and a manifest.json listing the metrics it returns. Packages are installed through Scoring Setup and selected as active per challenge.

    Example: scoring package manifest

    manifest.json
    {
  "package_id": "osipi_dce_ktrans",
  "name": "Approved DCE Ktrans scoring",
  "version": "1.0.0",
  "challenge_type": "dce",
  "map_type": "ktrans",
  "entry_point": "scoring.py",
  "call_mode": "standard",
  "official": true,
  "metrics": ["approved_metric_1", "approved_metric_2"]
}

    call_mode is standard for scripts taking --submission-dir, --output-dir and optionally --reference-dir. Only the metrics listed in the manifest are reported. Anything that is not approved OSIPI scoring takes "official": false.

    A scoring package is Python that executes on the server. Read the script before installing one.

    Reference data and masks

    Reference maps and ROI masks come from the organiser. Search order: the submission's own reference/ directory, the configured reference data directory, then the active scoring package's reference directory.

    Within a reference root, maps are read from maps/ and masks from masks/. Files are de-duplicated by physical file identity rather than path text, so on macOS and Windows the same mask cannot be admitted twice under two spellings.

    Locations are defined in backend/services/path_config.py. .gitignore excludes reference data, masks and imaging files from version control.
