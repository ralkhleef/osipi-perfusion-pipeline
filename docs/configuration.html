    In-app Configuration Manager

    Most challenge settings can be changed in the application. Some advanced settings can also be edited in the YAML file.

    Open QC & Preview → Reviewer settings → Challenge Configuration Manager to manage DCE, ASL or DSC without editing YAML. Each card opens one editor: maps, dataset structure, required files, analysis providers, private assets, capabilities, or saved versions.

    Saving a change

    A change is tested and saved before it is activated.

    1

    Test Configuration

    Checks the draft. The active rules are not touched.

    2

    Preview Changes

    Shows what differs from the rules currently in force.

    3

    Save as New Version

    Stores the draft as an inactive version.

    4

    Activate

    Applies the saved version, and only after it passes a second test.

    Saved versions stay inactive until you select Activate. If testing or activation fails, the current configuration stays active.

    The manager also lists private reference files and exports or imports configuration as a ZIP. Private images, masks, measured signals and scoring code are left out of those exports. Every report records which configuration and analysis versions produced it.

    Changing what a submission must contain

    Routine changes belong in the Configuration Manager. Editing config/validation_rules.yaml directly is for settings the manager does not expose.

    SettingWhat it controls
    MapsRequired and optional maps, dimensions, units, and filename aliases
    Dataset structureExpected participants, repeats, and sites
    Required artifactsMethods documents, modelled signals, and other required files
    Code executionWhether participant code must run or submitted result maps can be used directly
    AnalysisWhich built-in analyses are enabled and which configured inputs they use

    A missing required map is a blocking error; a missing optional map is not. The current ASL rules require CBF and ATT. DSC requires CBV, CBF, and MTT.

    Where compatible masks exist, ASL produces ROI statistics for CBF and ATT, DCE for Ktrans, and DSC for CBV, CBF and MTT. Which columns appear in a report is set by report_metrics: mean, median, SD, range and CoV.

    DCE can also compute a residual sum of squares when matching measured and modelled 4-D signals are present. That figure is descriptive and is deliberately not labelled deviance, which has no agreed definition yet.

    YAML controls requirements and enables analyses. Scientific formulas stay in tested code or a trusted versioned package.

    Example: make ve required for DCE

    config/validation_rules.yaml
    challenges:
  dce:
    required_maps: [ktrans, ve]
    optional_maps: [vp, kep]

    For more fields and examples, see the annotated challenge template and the developer configuration reference.

    Analysis and scoring

    General analysis and provider-specific scoring are kept apart, so turning one off does not silently turn off the other.

    TypeWhen it is available
    QC and previewsFor readable maps
    ROI statisticsWhen compatible ROI masks are available
    Generic reference comparisonWhen compatible reference maps are available, even if provider mode is none
    Built-in legacy TF6.2 providerFor its specific DCE Ktrans workflow and required organiser assets
    Trusted custom packageAfter a reviewed package is uploaded, validated, and selected for the matching challenge

    Provider mode none disables provider scoring only. It does not disable QC, previews, exports, compatible ROI statistics, or generic reference comparisons.

    Generic reference comparisons are not automatically official scores. Official OSIPI challenge ranking is not currently configured.

    A custom package runs Python on the server, so only trusted reviewer-approved packages should be installed. See Adding scoring metrics for the package format and the package template for a working example.

    Private reference data

    Reference maps, ROI masks and measured signals belong to the organiser, not the submitter. Add them through Private Reference Assets in the Configuration Manager, or put them in data/reference_data/. Subfolders are optional; the pipeline finds them either way.

    These files stay on the machine running the pipeline. Never commit private masks, reference maps, answer keys or unreleased challenge data to GitHub.

    Adding a file does not make a comparison official. What gets produced still depends on the challenge configuration and on which provider, if any, is selected.

    Applying a change

    How a change takes effect depends on what you changed.

    What changedHow to apply it
    A Configuration Manager draftTest → Preview → Save as New Version → Activate
    Mounted YAML in config/Press Reload rules in Reviewer settings
    A scoring packageUpload a new version, review its status, then select and activate it
    Private references or masksAdd them through Private Reference Assets or the local reference-data directory
    Application code under backend/, frontend/, or src/Run docker compose up --build

    Invalid rules or packages are rejected, leaving the previous active configuration unchanged. If YAML is baked into a container instead of mounted through Compose, rebuild the image before using Reload rules.

    Developer details are kept in the configuration reference, scoring update guide, and scoring-package guide.

    Developer reference

    Direct YAML editing supports required_maps, optional_maps, required_artifacts, datasets, and filename_identity_patterns. Use Scoring Setup for the legacy Reload rules route.

    Minimal custom-package manifest

    manifest.json
    {
  "package_id": "example_scoring_v1",
  "name": "Example analysis",
  "version": "1.0.0",
  "challenge_type": "dce",
  "map_type": "ktrans",
  "required_inputs": ["ktrans"],
  "entry_point": "scoring.py",
  "call_mode": "standard",
  "official": false,
  "metrics": ["rmse", "bias"]
}

    standard passes submission and output directories to a new package. osipi_cwd supports a reviewed legacy script that resolves paths from its package directory. Dependencies listed by a package are not installed automatically.
